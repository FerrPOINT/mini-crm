# План и прохождение полного цикла задачи

## Последовательность и зависимости

```text
ТЗ → анализ и допущения → модель/права → реализация
   → ревью → проверки и исправления → публикация/внутренняя приёмка
   → передача заказчику → внешняя приёмка
```

Это план именно задачи мини-CRM. Этапы и подтверждения восстановлены по
выполненной работе; оценки времени и прежние согласования не придуманы.

| ---------------------------------- | --------------------------------------------------------------------------------------------------------------- | --------------- | --------------------------------------------------------------------------------------------------------------------------- |

## Проверки перехода между этапами

### Готовность к реализации

- У ролей и сущностей есть определения; доступ исполнителя сформулирован.
- Разрешённые переходы и обязательный комментарий определены.
- База владеет правами и историей; фронтенд не заменяет эти проверки.
- Принятый способ размещения и происхождение UI зафиксированы.

Эти условия отражают реализованное решение; не означают, что до разработки
проводилось отдельное формальное согласование документа.

### Готовность к внутренней приёмке

- Нет известных незакрытых дефектов, мешающих проверенным сценариям ТЗ.
- TypeScript и сборка проходят; unit/API/E2E подтверждают поведение.
- В браузерном цикле проверены создание, выполнение, доработка, приёмка,
  переназначение и удаление, а также ошибки и мобильная навигация.
- Прямой API не обходит RLS, переходы и защищённую историю.
- Публичный артефакт соответствует проверенной версии; fixtures очищены.
- Описаны ограничения проверок и эксплуатации.

### Готовность к внешнему закрытию

- Заказчику переданы все четыре результата и рабочие доступы.
- Получен результат демонстрации/созвона и решение по приёмке.
- Замечания либо исправлены с проверками, либо явно согласованы как ограничения.

Последняя группа условий пока не подтверждена. Она не подменяется статусом
«тесты прошли».

## Порядок исправления замечаний

1. Связать замечание с F/S/D/U из requirements либо отметить новый объём.
2. Воспроизвести на конкретной версии и определить владельца нарушенного правила.
3. Добавить проверку, которая обнаруживает ошибку, и соседний допустимый сценарий.
4. Исправить причину; сохранить данные, права и историю миграций.
5. Выполнить затронутые проверки и собрать доказательства итогового состояния.
6. Обновить current-stage, test-cases и changelog; публикацию делать в пределах
   порученного окружения. Изменение ТЗ не скрывать внутри исправления.

## Выпуск и сохранение данных

Команды новой установки находятся в [README](../../../README.md).
Для существующего стенда сначала определить исходный commit, текущую схему,
целевую версию и совместимость. Применять только новые миграции по порядку.
Применённые миграции не редактировать и не переигрывать начальную схему.

Проверяемая конфигурация — `deploy/compose.yml` и приватный `.env.local`.
Текущий web читает собранный `dist`; обновление статических файлов и изменение
базы — разные действия. После разрешённого обновления сверить отданные файлы
и пользовательский сценарий, а не только состояние контейнера.

Для возврата frontend использовать ранее квалифицированный совместимый артефакт.
Откат SQL-функции требует отдельного исправляющего решения с сохранением текущих
данных и правил; автоматический обратный SQL не подготовлен. Удаление volumes,
повторный seed, reset, dumps и восстановление из копии не являются штатной
проверкой этой задачи. Эксплуатационное резервирование отдельно не настраивалось.
