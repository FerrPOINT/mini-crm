# Решения и допущения

1. Любой постановщик видит все объекты и задачи и может принять работу другого
   постановщика. Разделение по компаниям в задании не предусмотрено.
2. Исполнителем задачи может быть только пользователь с ролью исполнителя.
   Совмещение ролей и задачи без назначенного исполнителя не предусмотрены.
3. Автор, дата создания и начальный статус задаются базой и неизменяемы через
   клиентский API. Создание также записывается в историю.
4. При переназначении статус сохраняется. Новый исполнитель получает задачу
   вместе с историей; предыдущий теряет доступ. Статусы меняются только по ТЗ.
5. Постановщик может редактировать название, описание, объект и исполнителя
   в любом статусе. Принятую задачу можно редактировать, но нельзя заново открыть.
   История описывает смены статусов; отдельного журнала редактирования полей нет.
6. Удаление мягкое: задача или объект исчезает из интерфейса; удаление объекта
   скрывает и его задачи. История физически не удаляется. Восстановление из
   интерфейса не входит в задание.
7. Комментарий к переходу необязателен, кроме возврата на доработку. Пробелы,
   табуляции и переводы строк сами по себе не считаются комментарием;
   максимальная длина — 2000 символов. Проверка действует также в базе.
8. При конкурентной смене статуса устаревшее действие отклоняется. Повторная
   отправка не дублирует историю. Редактирование обычных полей использует
   последнее успешно сохранённое значение. Если объект задачи уже изменён
   другой сессией, перенос отклоняется с 409 до обновления карточки.
9. Имена исполнителя, автора и участников доступной истории читаются из профилей.
   Исполнитель не получает полный каталог пользователей или чужие задачи.
10. Даты хранятся с часовым поясом и показываются в часовом поясе браузера.
    Списки и история имеют серверную пагинацию по 20 записей.
11. Вместо облачного проекта Supabase используется самостоятельная установка
    на выделенном сервере. Supabase Auth, PostgreSQL и PostgREST
    сохранены; используемые UI-компоненты Base скопированы в `src/ui/`.
12. Публичная демонстрация использует временный HTTPS-адрес Cloudflare Tunnel.
    После пересоздания туннеля адрес меняется; постоянный домен не настраивался.

13. Форма закрепляет UUID за новой записью. Повтор с тем же ID и данными
    возвращает созданную запись без повторной истории. Изменённые данные или
    попытка восстановить удалённую запись через повтор дают конфликт.
14. Создание и редактирование задач выполняются командами базы: сначала
    блокируются объекты по UUID, затем задача. Прямые INSERT объектов/задач
    и UPDATE полей задачи закрыты для клиентской роли. Это согласует запись
    с каскадным мягким удалением объекта.
15. После записи обновляются только затронутые списки и карточки. Запрос профиля
    имеет независимый жизненный цикл и не участвует в обновлении задач.
16. Пароли соединений DB разделены. JWT-секрет Auth/PostgREST остаётся общим;
    разделение DB-паролей не означает полной изоляции серверных компонентов.
17. Журнал миграций ведёт Supabase CLI. Применённые файлы не переписываются.

## Границы результата

Восстановление пароля по почте, управление пользователями из CRM, вложения,
уведомления, сроки задач, поиск по задачам, журнал изменения обычных полей,
резервное копирование и мониторинг не входят в реализованный объём.
Демонстрационный стенд содержит тестовые данные. Постоянный домен, резервирование
и мониторинг требуют отдельной эксплуатационной настройки.
