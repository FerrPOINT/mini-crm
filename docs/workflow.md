# Пользовательский workflow и проверка CRM

## Участники и подготовка

Постановщик управляет объектами и задачами. Исполнитель работает только с
назначенными ему задачами. Постановщиков и исполнителей может быть несколько;
демонстрационные учётные записи — один постановщик и два исполнителя.
Пользователей создаёт администратор вне CRM; открытой регистрации нет.

Для демонстрации используйте отдельный тестовый стенд. Основные данные содержат
три объекта и пять задач в разных статусах. Пароли передаются отдельно,
не хранятся в документации или Git. Автотесты создают свои объекты и задачи;
после каждого сценария удаляют только записи с принадлежащими сценарию UUID,
включая скрытые через интерфейс записи и их тестовую историю.

## Сквозной путь

1. Постановщик входит по email и паролю. Видит список всех объектов. Неверный
   пароль оставляет пользователя на форме входа с понятной ошибкой.
2. Нажимает «Новый объект», вводит название и адрес, сохраняет. Открывает объект.
   Пока задач нет, карточка объясняет это; создание задачи доступно сразу.
3. При необходимости редактирует название или адрес. Отмена и Escape закрывают
   форму без сохранения и возвращают фокус на кнопку, открывшую форму.
4. Создаёт задачу: название, необязательное описание, объект и исполнитель.
   Объект предвыбран из карточки; исполнителя нужно выбрать. Поиск в выборе
   объекта/исполнителя и страницы по 20 вариантов позволяют работать со списками.
   Автор, дата и статус «Новая» назначаются базой; в истории появляется создание.
5. Исполнитель входит в свой кабинет, открывает «Мои задачи» либо объект со
   своей задачей. На общем объекте чужие задачи ему не показываются.
6. В карточке читает описание и историю, при желании оставляет комментарий,
   нажимает «Взять в работу». Статус становится «В работе», история обновляется.
7. После выполнения нажимает «Отправить на проверку». Получает статус
   «На проверке» и ожидает решения постановщика.
8. Постановщик открывает или обновляет карточку и выбирает:
   - «Принять задачу»: статус «Принята», дальнейших переходов нет;
   - «Вернуть на доработку»: сначала вводит содержательный комментарий,
     затем получает статус «На доработке». Пустая строка и пробелы не подходят.
9. При доработке исполнитель видит замечание, снова берёт задачу в работу,
   отправляет на проверку. Цикл повторяется до приёмки. Обе роли видят одинаковую
   доступную историю: участник, время, предыдущий и новый статус, комментарий.
10. При необходимости постановщик редактирует поля задачи, переносит её на
    другой объект или назначает другого исполнителя. Статус и история сохраняются.
    Новый исполнитель получает доступ, прежний его теряет, включая старую ссылку.
11. Постановщик может удалить задачу или объект. Сначала появляется подтверждение;
    отмена ничего не меняет. После подтверждения запись исчезает из списков.
    Удаление объекта также скрывает его задачи. История сохраняется в базе.
12. Пользователь выходит через меню аккаунта. При следующем входе другой роли
    список и доступные действия соответствуют новому пользователю; данные
    предыдущей сессии не должны оставаться в рабочем кабинете.

| Текущий статус | Действие                            | Кто выполняет           | Следующий статус |
| -------------- | ----------------------------------- | ----------------------- | ---------------- |
| Нет задачи     | Создать                             | Постановщик             | Новая            |
| Новая          | Взять в работу                      | Назначенный исполнитель | В работе         |
| В работе       | Отправить на проверку               | Назначенный исполнитель | На проверке      |
| На проверке    | Принять задачу                      | Постановщик             | Принята          |
| На проверке    | Вернуть с обязательным комментарием | Постановщик             | На доработке     |
| На доработке   | Взять в работу                      | Назначенный исполнитель | В работе         |

Иные переходы запрещены в базе и отсутствуют в интерфейсе.
Приёмка завершает цикл статусов; постановщик всё ещё может редактировать поля
или удалить задачу. Журнал отражает статусы, а не редактирование обычных полей.

## Поведение при ошибках и ожидании

- При загрузке показано ожидание, при сбое — ошибка с повторной попыткой.
  Сбой чтения истории не должен скрывать саму задачу.
- Ошибка сохранения оставляет форму и введённые значения. Повторное сохранение
  выполняет ту же операцию, не требует заново заполнять поля.
- На время записи поля и кнопки заблокированы. Escape и закрытие формы не должны
  прерывать незавершённое сохранение; повторный клик не создаёт вторую запись.
- Если другой пользователь уже изменил статус, устаревшая операция отклоняется.
  Карточка обновляет статус и историю; повторной записи в истории не появляется.
- Данные другого исполнителя и удалённые записи недоступны по прямой ссылке.
- Списки задач и история имеют страницы по 20 записей. Переход назад со второй
  страницы возвращает первые записи; последняя страница не теряет остаток.
- На телефоне меню открывается отдельной панелью и закрывается после выбора.
  Таблица сохраняет читаемые колонки и прокручивается внутри своей области.
  Ссылка назад находится слева; заголовок, кнопки и длинный текст переносятся.
- В меню аккаунта доступны светлая, тёмная и серая темы. Выбор сохраняется
  после обновления страницы на этом устройстве.

## Матрица автоматизации

Браузерные сценарии находятся в `tests/e2e/` и запускаются для desktop
(1280 × 800) и mobile (390 × 844, touch), на настоящем Auth и PostgreSQL API.
Подмена транспорта используется только для управляемого сбоя/задержки сети.
Основной workflow, права, сохранение и история выполняются без подмены ответа.

| Сценарий               | Что проверяется                                                                          | Автотест                   |
| ---------------------- | ---------------------------------------------------------------------------------------- | -------------------------- |
| Вход и выход           | Неверный пароль, успешный вход, reload сессии, смена роли без старого кабинета           | `AUTH`                     |
| Объект                 | Создание, редактирование, пустой список задач                                            | `FLOW`                     |
| Новая задача           | Поля, выбор исполнителя поиском, начальный статус, автор истории                         | `FLOW`                     |
| Выполнение             | «Новая → В работе → На проверке», очистка комментария                                    | `FLOW`                     |
| Доработка              | Пустой комментарий запрещён, замечание видно обеим ролям, повторная сдача                | `FLOW`                     |
| Приёмка                | Семь записей полного цикла, итоговый статус, отсутствие дальнейших действий              | `FLOW`                     |
| Изоляция UI            | Чужая карточка закрыта, исполнителю не показаны управление и приёмка                     | `FLOW`, `EDIT`, `AUTH`     |
| Перенос/переназначение | Название и описание сохранены, новый объект, смена доступа, история прежнего исполнителя | `EDIT`                     |
| Удаление               | Подтверждение и отмена для задачи и объекта, старые ссылки закрыты                       | `FLOW`                     |
| Валидация и клавиатура | Название/адрес из пробелов, отмена, вложенный выбор, нет результатов, возврат фокуса     | `FORM`                     |
| Раскладка              | Назад слева, компактный верх, длинные названия, читаемая мобильная таблица, меню         | `LAYOUT`                   |
| Темы                   | Три темы и сохранение выбранной после reload                                             | `LAYOUT`                   |
| Пагинация              | 21 задача, 22 записи истории, точные диапазоны, разные записи, возврат назад             | `PAGES`                    |
| Устаревшая карточка    | Конфликт, актуальные статус и история, без дубля                                         | `STALE`                    |

| Сбой истории           | Задача и действие доступны, история загружается отдельным повтором                       | `HISTORY`                  |
| Прямое обращение к API | RLS, отсутствие чужих данных, запрет повышения роли и редактирования исполнителем        | `tests/security.test.mjs`  |
| Защита статусов        | Все разрешённые и запрещённые пары роль/статус, обязательный комментарий                 | `tests/security.test.mjs`  |
| Защита истории         | Запрет подделки/изменения/удаления, неизменяемый автор и дата                            | `tests/security.test.mjs`  |
| Конкуренция            | Два перехода одновременно, один успех и одна запись истории                              | `tests/security.test.mjs`  |
| Скрытие с аудитом      | Переназначение и удаление проверены напрямую, история физически сохранена                | `tests/security.test.mjs`  |

## Воспроизводимый прогон

1. Поднять отдельный стенд по README, применить миграции, создать демонстрационные
   учётные записи через `pnpm seed`. Не запускать seed на базе с рабочими данными.
2. Выполнить `pnpm typecheck`, `pnpm test` и `pnpm test:api`.
3. Установить браузер тестового runner: `pnpm exec playwright install chromium`.
   Если ОС сообщает об отсутствующих системных библиотеках, установить зависимости
   Playwright согласно документации для выбранной ОС.
4. Выполнить `pnpm test:e2e`. По умолчанию проверяется `http://127.0.0.1:8788`.
   Для другого выделенного стенда установить `E2E_BASE_URL`; frontend должен быть
   собран против той же базы, чьи ключи и пароли указаны в `.env.local`.
5. Для отдельного сценария: `pnpm test:e2e --project=desktop --grep 'FLOW:'`.
   Полный прогон выполняет оба размера экрана, одним worker, без автоматических
   повторов. Ошибка сценария остаётся ошибкой, а не маскируется перезапуском.
6. HTML-отчёт находится в `playwright-report/`, снимки падений — в `test-results/`.
   Это приватные, игнорируемые Git артефакты. Не публиковать отчёт без проверки
   на учётные данные. Состояние авторизации не записывается в отдельные файлы;
   запись сетевых traces и видео отключена.

Автотесты браузера проверяют Chromium и эмуляцию мобильного viewport.
Реальные iOS/Android, Firefox/WebKit, скринридеры и длительная нагрузка не входят
в этот прогон. Временный Cloudflare URL и отсутствие восстановления пароля,
уведомлений и интерфейса управления пользователями описаны в `decisions.md`.
Для реальных клиентских данных отдельно нужны постоянный адрес и эксплуатационная
подготовка; результат остаётся демонстрацией по тестовому заданию.
