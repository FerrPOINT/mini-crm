# Стройка · мини-CRM

CRM для управления работами на строительных объектах. Постановщик назначает
задачи, исполнитель выполняет их и передаёт результат на проверку.

React + TypeScript · Supabase Auth · PostgreSQL · PostgREST

[Демонстрация](https://reg-sensitive-cpu-governor.trycloudflare.com) ·
[Пользовательский сценарий](docs/workflow.md) ·
[Архитектурные решения](docs/decisions.md) ·
[Требования и проверки](docs/tasks/mini-crm/current-stage.md)

Демонстрация доступна по временному HTTPS-адресу. Учётные данные выдаются отдельно.

## Возможности

- Объекты с адресами и списками задач.
- Создание, редактирование, перенос и назначение задач.
- Личный список работ исполнителя.
- Проверка результата, возврат с замечаниями и повторная сдача.
- История статусов с участником, временем и комментарием.
- Мобильная навигация, светлая, тёмная и серая темы.

| Роль        | Доступ                                                            |
| ----------- | ----------------------------------------------------------------- |
| Постановщик | Все объекты и задачи, управление и приёмка работ                  |
| Исполнитель | Свои задачи и связанные объекты, начало работы и сдача результата |

Цикл задачи: **Новая → В работе → На проверке → Принята**.
При возврате на доработку цикл продолжается через «На доработке → В работе».
Комментарий к возврату обязателен.

## Архитектура и защита

Frontend обращается к Supabase через типизированный клиент. Auth отвечает за
вход, PostgreSQL — за права и правила работы с данными. Nginx отдаёт приложение
и проксирует `/api` на том же origin.

- RLS и права столбцов ограничивают чтение и запись независимо от интерфейса.
- Смена статуса и запись истории выполняются одной транзакцией с блокировкой задачи.
- Историю, автора и дату создания нельзя подделать обычным клиентским запросом.
- Устаревший переход получает HTTP 409, повтор не создаёт событие истории.
- Регистрация закрыта. Серверные ключи используются только служебными скриптами.
- Удаление скрывает записи, сохраняя историю в базе.

## Запуск с облачным Supabase

Требуются Node.js 22.22+ и pnpm 10.28.1.

```sh
pnpm install --frozen-lockfile
cp .env.example .env.local
```

Укажите `VITE_SUPABASE_URL` и публичный `VITE_SUPABASE_ANON_KEY`.
Примените файлы `supabase/migrations/` по порядку через SQL Editor или Supabase CLI.
Отключите открытую регистрацию. Создайте подтверждённых пользователей в Auth
и соответствующие записи `profiles` с теми же UUID, именем и ролью
`manager` или `executor`.

```sh
pnpm dev
```

Приложение откроется на `http://127.0.0.1:5177`.

## Собственный сервер

Compose включает PostgreSQL, Auth, PostgREST и Nginx. База не публикуется
наружу, административный Auth API слушает только loopback.
Studio, Storage и Realtime не требуются.

На **новой установке**, из корня репозитория:

```sh
python3 scripts/init-environment.py
pnpm install --frozen-lockfile
pnpm build
docker compose --env-file .env.local -f deploy/compose.yml up -d db auth rest
for migration in supabase/migrations/*.sql; do
  docker compose --env-file .env.local -f deploy/compose.yml exec -T db \
    psql -U postgres -d postgres -v ON_ERROR_STOP=1 < "$migration" || exit 1
done
docker compose --env-file .env.local -f deploy/compose.yml up -d web
pnpm seed
```

Адрес приложения — `http://127.0.0.1:8788`. Для удалённого доступа используйте
SSH forwarding или HTTPS reverse proxy. Не передавайте пароли через публичный HTTP.

`.env.local` создаётся один раз с правами `0600`. Он содержит серверные ключи
и демонстрационные пароли и не включается в Git. `SUPABASE_SERVICE_ROLE_KEY`
не должен иметь префикс `VITE_` или попадать во frontend.

При обновлении существующей установки применяйте только новые миграции.
Не повторяйте начальную схему и не удаляйте volumes с данными.

Необязательный профиль `public` запускает Cloudflare Quick Tunnel:

```sh
docker compose --env-file .env.local -f deploy/compose.yml --profile public up -d tunnel
```

После пересоздания туннеля адрес меняется. Для постоянного адреса нужен свой
домен с именованным туннелем или reverse proxy.

## Проверки

```sh
pnpm typecheck
pnpm test
pnpm build
pnpm test:api
pnpm exec playwright install chromium
pnpm test:e2e
```

API и E2E запускаются на отдельном тестовом стенде с демонстрационными
пользователями и приватным `.env.local`. Они проверяют настоящую базу и очищают
собственные тестовые записи. E2E покрывают Chromium desktop/mobile; адрес
стенда задаётся через `E2E_BASE_URL`, по умолчанию `http://127.0.0.1:8788`.

[Матрица сценариев и ограничения проверки](docs/tasks/mini-crm/test-cases.md).
HTML-отчёты и снимки падений игнорируются Git; перед публикацией их нужно
проверять на учётные данные.
